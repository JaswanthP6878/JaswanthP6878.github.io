One of the most fascinating parts of the Go programming language, to me, is the goroutine. You start one just by putting the keyword `go` in front of a function call. Functions in Go aren't "colored" (see Bob Nystrom's [What Color is Your Function?](https://journal.stuffwithstuff.com/2015/02/01/what-color-is-your-function/)): any ordinary function can be run as a goroutine. For example, let's take a simple timer that beeps to stdout after one second, and spawn it in the background:

```go
func startBeeper() {
	var makeSureGoroutineIsRunning sync.WaitGroup
	makeSureGoroutineIsRunning.Add(1)
	go func() { // #1
		makeSureGoroutineIsRunning.Done()
		time.Sleep(1 * time.Second)
		fmt.Println("Beep, time's up!!")
	}()
	makeSureGoroutineIsRunning.Wait()
}

func main() {
	startBeeper()
	// do some other work
	// ...
}
```

Here we can see how simple it is to start a goroutine at `#1`. We define a func (a nice way to package the goroutine's body) and start it with the `go` keyword. The goroutine gets scheduled and runs towards completion, and after one second a beep gets printed. All the extra code is just boilerplate to make sure the goroutine is actually running before `startBeeper` returns: nothing complicated, just a flavor of `fork-join` in Go's world.

But what actually happens when we write `go`? Where does that function run, how much memory does it take, and who decides when it gets a CPU? That's what this post is about.

## Anatomy of a goroutine

To the runtime, a goroutine is just two things: a small struct that describes it, and a stack.

The struct is called `g`. Trimmed down to the fields that matter for this post, it looks like this:

```go
// runtime/runtime2.go (trimmed, comments mine)
type g struct {
	stack        stack         // bounds of this goroutine's stack
	stackguard0  uintptr       // checked on function entry: room left?
	m            *m            // thread running it right now, if any
	sched        gobuf         // saved sp, pc, ... while not running
	atomicstatus atomic.Uint32 // runnable, running, waiting, ...
	goid         uint64
	preempt      bool          // "please yield" flag
	// ... and many more
}
```

Notice there's no thread in there that the goroutine *owns*, just the `m` it happens to be running on right now. A goroutine isn't tied to a thread: over its lifetime it can run on many different ones. And all goroutines share the same address space as the rest of your program. There's no private memory per goroutine, which is exactly why they can share data (and why we need channels and mutexes to do that safely).

The stack is where it gets interesting. An OS thread gets a big, fixed-size stack up front: 8 MB is the usual default on Linux. A goroutine's stack starts tiny, as small as 2 KB, and it doesn't live on any thread's stack either: the runtime allocates it from memory it manages itself.

So what happens when a goroutine needs more than 2 KB? Nearly every Go function starts with a short check that the compiler inserts, comparing the stack pointer with `stackguard0`. If the next frame won't fit, the function calls into the runtime (`morestack`), which allocates a new stack twice the size, copies the old one over, fixes up any pointers into it, and carries on. Stacks can grow up to 1 GB on 64-bit systems, and the garbage collector shrinks them again when they're mostly unused. Since Go 1.19 the runtime also tracks the average stack size it sees and starts new goroutines at that size, so a typical goroutine doesn't pay for growing over and over.

Here's the back-of-the-envelope difference for a hundred thousand concurrent tasks:

$$
\underbrace{10^5 \times 2\ \text{KB}}_{\text{goroutines}} \approx 200\ \text{MB}
\qquad \text{vs.} \qquad
\underbrace{10^5 \times 8\ \text{MB}}_{\text{OS threads}} \approx 800\ \text{GB}
$$

The thread number is reserved address space rather than memory actually touched, but it still isn't free: every thread is also bookkeeping in the kernel. Switching is cheaper too. When a goroutine stops running, the runtime saves a handful of registers (the stack pointer, the program counter and a few others) into `g.sched` and loads another goroutine's, all in user space. Switching threads has to go through the kernel.

So goroutines are cheap. But they're not threads, and only threads actually run on CPUs, so something has to decide which goroutine runs on which thread, and when.

## Usage of goroutines

The point that gets brought up everywhere Go is used is the **volume** of goroutines running at any point of the execution. By their very design, goroutines are meant to be spawned liberally: tens of thousands, sometimes hundreds of thousands, each starting with only a few KB of stack. What does this scalability give us? We can spawn them wherever and whenever we need. Take a web server: we can spawn a separate goroutine for each request we're handling, and each of those can spawn more as the application needs.

Even though this is great, it leads to one more problem: how do we allocate actual resources to them? How do we assign compute to tens of thousands of these tasks on a machine with maybe 8 or 64 cores? The usual answer in an OS or multithreading class is `OS threads`. But OS threads are limited: they're a big and bulky way of handling multithreading, and they add a substantial amount of overhead once you have a large number of parallel tasks.

Go's solution is to have a runtime that schedules and manages the goroutines, multiplexing many goroutines onto a few OS threads. The design is called the **GMP** model, and expanding the three letters already tells us most of what the model gives us:

$$
\underbrace{G}_{\substack{\text{Goroutine}\\
\text{lightweight unit of execution}}}
\qquad
\underbrace{M}_{\substack{\text{Machine}\\
\text{OS / worker thread}}}
\qquad
\underbrace{P}_{\substack{\text{Processor}\\
\text{logical scheduling resource}}}
$$

The main idea of the GMP model is to separate the concerns: goroutines (G) are scheduled onto processors (P), and threads (M) do the actual running, given that $|G| \gg |M|$.

G and M are what you'd expect. P is the clever part. It isn't a CPU; it's closer to a *license to run Go code*. The comment at the top of the scheduler's source says it in one line: an M must have an associated P to execute Go code. That gives one invariant that shapes everything else:

$$
\bigl|\{\, m \in M : m \text{ is running Go code} \,\}\bigr| \;\le\; k,
\qquad k = |P| = \mathtt{GOMAXPROCS}
$$

There can be more threads than Ps (a thread blocked in a system call, for example, doesn't hold one), but at most $k$ of them run Go code at once. By default $k$ is the number of CPU cores, and since Go 1.25 it also respects a container's CPU limit on Linux.

Why the extra P layer at all? Before Go 1.1 there wasn't one. Every thread pulled goroutines from one global queue behind one global mutex, and threads kept handing goroutines off to each other. On an 8-core server, the runtime ended up spending a real chunk of CPU just fighting over that lock. Dmitry Vyukov's 2012 design doc (linked at the end) introduced P to give each core its own queue, plus work stealing on top. That's still the design today.

## The Runtime Design

Goroutines that are created have to be queued before the runtime can run them, and the Go runtime uses a two-level queue for that: a **local per-P queue** and a **global queue**.

Each P owns its local queue $Q_i$: a fixed ring buffer with 256 slots. Only the P that owns it adds to it, so most scheduling needs no lock at all. Next to the queue there's a single **`runnext`** slot $r_i$, for the goroutine that should run next, ahead of everything queued. When a goroutine is spawned, it goes into its parent's P, right into `runnext`, so it runs soon, on the same core, while the data it shares with its parent is still in cache. Whatever was in `runnext` before moves to the back of $Q_i$. This keeps things cache-friendly and simplifies the design.

The global queue $Q_g$ is shared by every P and protected by a lock. It catches the goroutines that don't have a natural home on a P:

- **Overflow.** When a P's local queue is full, half of it (128 goroutines) moves to the global queue to make room.
- **Goroutines coming back from the outside world.** A goroutine that made a blocking system call has given up its P while it waited (more on that later). When the call returns, it tries to get a P back; if none is free, it goes to the global queue. No running goroutine spawned it, so there's no local queue it naturally belongs to.

This two-level hierarchy gives us a nice performance gain. Because each P has its own queue, the common case (spawn a goroutine, run the next one) is a quick, mostly lock-free operation, instead of every worker thread synchronizing on a single global queue all the time.

### Picking the next goroutine

A thread holding $p_i$ runs a goroutine until it finishes, blocks (on a channel, a lock, I/O, a timer) or gets preempted. Then it calls `schedule()`, which asks `findRunnable()` what to run next. The answer is checked in a fixed order, cheapest first:

1. **Fairness check.** Every 61st time, look at the global queue first. Otherwise two goroutines that keep respawning each other could occupy the local queue forever and starve the global one.
2. **`runnext`, then the local queue.** No lock needed.
3. **The global queue.** Take a batch of $n = \min\left(128,\ |Q_g|,\ \lfloor |Q_g| / k \rfloor + 1\right)$ goroutines rather than just one: a fair share of the global queue, and never more than half of what fits locally, so the thread doesn't have to come back to the lock right away.
4. **The network poller.** Goroutines whose network I/O is ready (more on this below).
5. **Steal from another P.** The subject of the next section.
6. **Give up.** Release $p_i$ to the list of idle Ps and put the thread to sleep.

### The problem with local queues

These two-level queues give rise to a problem: skew. Consider the earlier web server spawning a goroutine for each connection. A single `connectionHandler` goroutine accepts connections and spawns a handler goroutine for each one. With the design so far, every handler lands on the same P as `connectionHandler`, and they only spill over to the global queue once 256 of them have piled up:

```text
Every handler lands on the acceptor's P:

  P0 │ connectionHandler  h1 h2 h3 h4 h5 h6 h7 h8
  P1 │ (idle)
  P2 │ (idle)
  P3 │ (idle)
```

The connection handlers aren't spread across the cores: one P is overloaded while three sit idle. To address this, the Go runtime scheduler uses **work stealing** to spread the work around.

## Work stealing scheduling

The general idea of work stealing is that a worker that has nothing to do *steals* work from another worker's queue. Nobody is pinned to anybody: an idle worker picks a victim at random and takes some of its work.

There are two ways to balance load. Busy workers can push work to idle ones (*work sharing*), or idle workers can take it from busy ones (*work stealing*). The appeal of stealing is that the cost lands on the workers that have nothing better to do: a busy P never stops to think about balancing, it just runs goroutines.

Let's formalize the model before defining the algorithm. Work stealing was formalized for the **fork-join** model of concurrency, and Go maps onto it naturally: spawning a goroutine with the `go` keyword is a fork, and waiting for it to finish (like the `WaitGroup` in our beeper) is a join. Real Go programs aren't always this tidy, since goroutines also talk to each other over channels, but fork-join is where the algorithm comes from. In the classic version, each worker owns a double-ended queue (deque) of tasks, and the main steps are:

1. At a fork point, push the new task onto the tail of the worker's own deque.
2. When the current task finishes or waits at a join, pop the next task from the tail of the worker's own deque: newest first, since it's the most likely to still be in cache.
3. If the deque is empty, become a thief: pick a victim worker uniformly at random and steal the task at the *head* of its deque, the oldest one, which usually represents the biggest chunk of remaining work.
4. If the victim's deque was empty too, pick another victim at random and try again.

### How Go does it

Go keeps the idea but changes a few details:

- **The queue belongs to the P, not the thread.** A thread can lose its P (during a system call, for example), but the queued work shouldn't be stuck with that thread, so it stays with the P.
- **The local queue is first-in, first-out**, with `runnext` as a one-slot "newest first" shortcut on top of it.
- **Thieves take half, not one.** Taking $\lceil |Q_j| / 2 \rceil$ goroutines means the thief won't need to steal again right away, while the victim keeps the rest. The steal is lock-free: the thief copies goroutines out of the victim's ring buffer and claims them with a single compare-and-swap on the queue's head.
- **Random order, every P once.** Each pass starts at a random P and walks the others with a stride that shares no factor with $k$, so every P is visited exactly once and thieves don't all pile onto the same victim. A thief makes up to four passes.
- **`runnext` is protected until the last pass.** Only the final pass may take a victim's `runnext` (and its timers). That goroutine was just readied by whatever is running on the victim, which probably wants it back soon.
- **Not every idle thread hunts for work.** A thread looking for work is *spinning*, burning CPU, so the runtime limits spinning threads to half the busy Ps: a new thread may only start spinning if $2s < k - \ell$, where $s$ is the number of spinning threads and $\ell$ the number of idle Ps. That's enough to pick up new work quickly, without an idle program burning all your cores.


Here $t_i$ counts how many times $p_i$ has scheduled. Back to our web server: when `connectionHandler` spawns handlers, the runtime notices there are idle Ps and wakes a thread for one of them. That thread finds nothing locally, steals half of P0's queue, and the next idle P does the same with whichever queue it finds first:

```text
After a few steals, each thief taking half of a victim's queue:

  P0 │ connectionHandler  h7 h8
  P1 │ h3 h4      took 4 of P0's 8, then lost 2 to P3
  P2 │ h5 h6      took 2 of P0's remaining 4
  P3 │ h1 h2      took 2 of P1's 3 queued
```

Within a few steals, the work is spread across every core without P0 ever doing anything but running goroutines.


## When goroutines block

So far, goroutines only stop running by finishing. Real ones block constantly, and how the runtime handles blocking is what makes "just spawn a goroutine" cheap:

- **Channels, mutexes and `time.Sleep`.** The goroutine is *parked*: marked as waiting and set aside (timers are kept on each P). The thread doesn't block; it goes straight back to `schedule()` and runs something else. When the channel gets a value or the timer fires, the goroutine goes back on a run queue.
- **Network I/O.** Underneath, Go's sockets are non-blocking. A goroutine waiting on one is parked and registered with the **netpoller** (epoll on Linux, kqueue on macOS, IOCP on Windows), and step 4 of the scheduling loop collects the ones whose data has arrived. Ten thousand idle connections cost ten thousand parked goroutines, not ten thousand blocked threads.
- **Blocking system calls** (file I/O, cgo). These really do block the thread, so the runtime separates the P from it. A background monitor thread, `sysmon`, notices a P stuck in a system call for longer than one of its ticks (at least 20 µs) while other work is waiting, and hands the P to another thread so the rest of the program keeps running. When the call returns, the goroutine tries to get a P back; if none is free, it goes to the global queue, as we saw earlier, and its thread goes to sleep.
- **Goroutines that never block.** A tight loop could hog a P forever. `sysmon` also watches for goroutines that have run for more than 10 ms and asks them to yield. Since Go 1.14 this is asynchronous: the runtime sends the thread a signal (`SIGURG`) and interrupts the goroutine at a safe point, even in a loop with no function calls.

## Conclusion

Let's go back to the beeper from the start and follow it through the scheduler:

1. `go func() { ... }()` calls into the runtime: a `g` is created (or reused from a free list) with a small stack and put in our P's `runnext`. If another P is idle, the runtime wakes a thread in case there's work to share.
2. `startBeeper` blocks on `Wait()`, so the main goroutine is parked and our thread calls `schedule()`. It finds the new goroutine in `runnext` and starts it, most likely on the same core.
3. `Done()` makes the main goroutine runnable again, and `time.Sleep` parks the beeper on a timer, freeing the thread for `main`.
4. A second later the timer fires, the beeper goes back on a run queue (maybe on a different P, if it got stolen in between), prints `Beep, time's up!!` and exits. Its `g` goes back on the free list for the next `go` statement.

None of this is visible from the `go` keyword, and that's the point. Goroutines are cheap because of three decisions: small stacks that grow on demand, a P per core so that scheduling rarely needs a lock, and idle cores that steal work instead of busy cores having to share it. Together, they're how a web server can afford a goroutine for every request.
